# 队列积压怎么查

> 这是同步链路最常见的故障。**别急着重启，先看数字。**

## 先分清两种积压

| 现象 | 含义 | 方向 |
|---|---|---|
| **LAG 持续上涨** | 生产速度 > 消费速度 | 消费端性能问题 |
| **LAG 不涨也不降** | 消费端完全卡住 | 消费端挂了/死锁 |
| **LAG 归零但有延迟** | 队列正常，下游写入慢 | 查目标库 |

## 排查顺序（照做）

**① 确认积压量**

```bash
# Kafka
kafka-consumer-groups.sh --bootstrap-server <地址> --describe --group <组名>
```

看 **LAG** 那一列。

**② 确认消费进程活着**

```bash
ps -ef | grep <进程关键字> | grep -v grep
```

**进程在 ≠ 在干活。** 还要看：

```bash
top -p <PID>              # CPU 是不是一直很高（可能是死循环）
lsof -p <PID> | grep -c REG   # 打开的文件数是不是暴涨（可能句柄泄漏）
```

**③ 看消费端日志**

```bash
tail -n 200 <消费端日志> | grep -iE 'error|exception|timeout|retry'
```

**④ 看下游**

如果消费进程正常但就是慢：

- 目标库连接池满了？（`v$resource_limit`）
- 目标库有锁？（`v$session` 里 `blocking_session`）
- 磁盘 IO 打满？（`iostat -x`）

## 三种典型结论

**结论 A：消费进程挂了**
→ 看日志找原因，修完重启。**先确认生产端数据没丢。**

**结论 B：消费进程活着但处理慢**
→ 看单条处理耗时。是不是某类数据特别慢？是不是 N+1 查库？

**结论 C：一切正常但 LAG 就是高**
→ 消费能力不够。**加实例** 或 **提并发**，别硬等。

## ⚠️ 不要做的事

- ❌ **不要一上来就 `--from-beginning` 重读** —— 生产 IO 压力巨大
- ❌ **不要先重置位移** —— 会丢数据或重复处理
- ❌ **不要盲目扩容** —— 没找到瓶颈，扩容只是把问题推迟
