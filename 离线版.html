使用说明

怎么用这份知识库

这是什么

一个 HTML 文件，双击就打开。
不需要网络、不需要账号、不需要任何服务。
手机上也能开：把它发到自己微信里点开就行。

可选：如果你想做成一个网站

不想开外网就跳过这一节 —— 离线文件已经够用了。
只有在「想用手机随时打开、又不想每次都找文件」时，才需要往下做。

第 1 步：建仓库
GitHub 上新建一个仓库，名字随意（比如 kb），建议选 Private。

第 2 步：上传
把这个文件夹里所有文件上传到仓库根目录。
（网页上点 Add file → Upload files，整个文件夹拖进去就行）

第 3 步：开 Pages
仓库 → Settings → 左侧 Pages → Source 选 Deploy from a branch → 分支选 main、目录选 / (root) → Save。

等 1 分钟，访问：

https://你的用户名.github.io/kb/

手机存成书签，以后随时点开。

⚠️ 注意：Private 仓库 + Pages 需要 GitHub 付费版。
免费版只能用 Public 仓库 —— 所以内容必须脱敏（不写 IP、客户名、真实数据）。
这也是我们一开始就定的规矩：只写方法和思路。

日常更新

改 .md 文件 → 提交 → 1 分钟后网站自动更新。不用重新部署。

手机上也能写

GitHub 手机 App 里可以直接编辑 Markdown 文件。
出差在路上想记一条，打开 App 改一下就行。

换个域名（可选）

在仓库根目录加一个 CNAME 文件，里面写你的域名。
如果你有自己的域名，绑定上去，链接更好记。

03

Linux 命令

只读诊断命令

全部是只读命令，生产上可以直接跑。

先确认自己在哪台机

hostname -I          # 看 IP，避免在错误的机器上操作
uptime               # 跑了多久、负载多少
who                  # 谁在线

负载怎么看：load average 三个数是 1/5/15 分钟平均。
超过 CPU 核数就是过载。核数：nproc

看进程和端口

ps -ef | grep java | grep -v grep        # 所有 Java 进程（带 jar 路径）
ss -lntp                                 # 监听的端口 + 对应进程
ss -lntp | grep 9090                     # 只看某个端口
lsof -p <PID> | head -30                 # 某进程打开了哪些文件

看资源

df -h                    # 磁盘（先看这个，最常见）
df -i                    # inode（磁盘没满但写不进去，就是它）
free -h                  # 内存
top -b -n1 | head -20    # CPU 占用前几名
iostat -x 1 3            # 磁盘 IO（需要 sysstat）

看日志

tail -f /path/app.log                    # 实时跟
tail -n 200 /path/app.log                # 看最后 200 行
grep -i error /path/app.log | tail -30   # 只看错误
grep "$(date +%F)" /path/app.log | tail  # 只看今天

⚠️ 不要 cat 几百 MB 的日志，会把终端卡死，也会给机器压力。
用 tail / grep / less。

找文件和目录

find /opt -name '*.jar' 2>/dev/null | head -20
find /opt -type d -iname '*log*' 2>/dev/null
du -sh /opt/* 2>/dev/null | sort -h | tail -10   # 哪些目录最占空间

服务管理（CentOS 7）

systemctl status <服务名>     # 状态（只读）
systemctl list-units --type=service --state=running   # 在跑的服务
journalctl -u <服务名> -n 100 --no-pager              # 服务日志

什么时候用什么

现象 先看
程序起不来 systemctl status + journalctl
连不上 ss -lntp 看端口在不在听
写不进去 df -h、df -i
变慢了 top、iostat、uptime
不知道装在哪 ps -ef 看启动命令里的路径

Kafka 命令

3.5.1 版

⚠️ 3.5.1 没有 --zookeeper 参数了，全部用 --bootstrap-server。
下面标 🟢 的只读，🟡 的会改状态。

设个变量，少打字

export KAFKA_HOME=/opt/kafka          # 改成你的实际路径
export BS=10.0.0.1:9092               # 改成你的 broker 地址

🟢 健康检查

$KAFKA_HOME/bin/kafka-broker-api-versions.sh --bootstrap-server $BS | head

$KAFKA_HOME/bin/kafka-topics.sh --bootstrap-server $BS --list

$KAFKA_HOME/bin/kafka-topics.sh --bootstrap-server $BS --describe --topic <topic名>

$KAFKA_HOME/bin/kafka-topics.sh --bootstrap-server $BS --under-replicated-partitions

--describe 重点看三列：
- Leader：-1 说明这个分区没有主，等于不可用
- Replicas / Isr：Isr 少了副本 = 有 broker 掉了
- Under-replicated 有输出 = 副本不同步，要查

🟢 消费组（排查积压必用）

$KAFKA_HOME/bin/kafka-consumer-groups.sh --bootstrap-server $BS --list

$KAFKA_HOME/bin/kafka-consumer-groups.sh --bootstrap-server $BS --describe --group <组名>

LAG = 积压量。LAG 一直涨 = 消费跟不上（消费端慢了或者挂了）。
LAG 不涨但也不降 = 消费端卡住了。

🟡 改状态（生产上先问研发）

# 修改 topic 分区数（只能增不能减）
$KAFKA_HOME/bin/kafka-topics.sh --bootstrap-server $BS --alter --topic <topic> --partitions 6

# 动态改配置（不用重启）
$KAFKA_HOME/bin/kafka-configs.sh --bootstrap-server $BS --alter --entity-type topics --entity-name <topic> --add-config retention.ms=604800000

🟡 重置消费位移（危险，先 dry-run）

$KAFKA_HOME/bin/kafka-consumer-groups.sh --bootstrap-server $BS --group <组名> \
  --reset-offsets --to-earliest --topic <topic> --dry-run

# 确认无误后，把 --dry-run 换成 --execute

⚠️ 必须停掉消费者再重置，否则会乱。
⚠️ 生产上不要随便用 --from-beginning 读数据，IO 压力大。

常见故障对照

现象 先查
消费积压涨 --describe --group 看 LAG；再查消费端进程
分区不可用 --describe --topic 看 Leader 是不是 -1
副本不同步 --under-replicated-partitions
生产发不进去 看 broker 是否 acks 超时、磁盘满没满

Oracle 命令

只读查询

全部只读。用监控账号跑，别用 sysdba。

连库

sqlplus 用户名/密码@//主机:1521/服务名

进库后先设置好显示格式：

SET LINESIZE 200
SET PAGESIZE 100
SET NUMWIDTH 12

看表空间（最常查）

SELECT tablespace_name,
       ROUND(SUM(bytes)/1024/1024/1024, 2) AS 总GB
  FROM dba_data_files
 GROUP BY tablespace_name;

SELECT tablespace_name,
       ROUND(SUM(bytes)/1024/1024/1024, 2) AS 空闲GB
  FROM dba_free_space
 GROUP BY tablespace_name;

看会话和锁

-- 当前会话
SELECT sid, serial#, username, status, machine, program
  FROM v$session
 WHERE username IS NOT NULL;

-- 有没有阻塞
SELECT blocking_session, sid, serial#, event, seconds_in_wait
  FROM v$session
 WHERE blocking_session IS NOT NULL;

-- 锁等待
SELECT * FROM v$lock WHERE block > 0;

看慢 SQL

SELECT sql_id, elapsed_time/1000000 AS 秒, executions, sql_text
  FROM v$sql
 ORDER BY elapsed_time DESC
 FETCH FIRST 20 ROWS ONLY;

看进程数（ORA-00020 报错时查）

SELECT resource_name, current_utilization, limit_value
  FROM v$resource_limit
 WHERE resource_name IN ('sessions','processes');

找表

-- 按名字模糊找表
SELECT owner, table_name FROM all_tables
 WHERE table_name LIKE '%RULE%' ORDER BY owner, table_name;

-- 看表结构
SELECT column_name, data_type, data_length
  FROM all_tab_columns
 WHERE table_name = '表名大写' ORDER BY column_id;

⚠️ 纪律

  • 只读：只用 SELECT。要 UPDATE/DELETE 先找研发确认。
  • 别查全表：大表加 WHERE 和 FETCH FIRST。
  • 别在业务高峰跑重查询：会拖慢业务。

派工 / 指标 / 组件

遇到不懂的词就加一行。一行一个，别写长。

派工核心

术语 一句话 在哪出现

Lot 批次，一次跑的一批晶圆 界面、日志

Dedication 专机专用，只能上指定机台 规则
Changeover 换型，换 recipe 花的时间 排序规则

Hold 扣留，品质异常被卡住的货 状态
PM 预防性维护，机台定期停机 机台状态
Tie-break 同分时按什么决先后 排序规则

术语 一句话

07

数据同步架构

全链路 + 自测题

⚠️ 脱敏版：这里不写真 IP、不写客户名。只写结构和数据流。

一、整体链路（增量）

MES(Oracle)
   │  ① 增删改触发器，写变更事件
   ▼
qtable（变更事件表）        ← 不同表对不同的 qtable
   │  ② 每 200ms 抽取已提交数据
   ▼
data-sender ──序列化成 JSON──▶ Kafka
                                 │  ③ 最长 1s 一批
                                 ▼
                          data-sinker ──▶ 目标库（写库）
                                 │  ④ 发同步履历
                                 ▼
                              Kafka
                                 │
                                 ▼
                          data-history ──▶ MongoDB

要点：
- sender / sinker / history 都是 Java jar
- 每个 qtable 对应一整套 jar → 进程数 = qtable 数 × 3 × 实例数
- 同步只走主写库；业务 RTD 读读库；还有备库
- 三个库之间靠 数据库自带复制保持一致

二、全量链路

admin 客户端 ──请求──▶ sender
                        │ 从 MES 导出 CSV
                        ▼
                      sinker ──▶ 目标库写入
                        │
                        ▼
                      history ──▶ MongoDB

三、事件闭环（trigger 配置怎么生效）

sinker 发现满足触发条件
   │ HTTP
   ▼
aqm（低代码平台，含 repository event 节点的流程）
   │ 固定调 VIP:23456
   ▼
keepalived + haproxy（2 台）分发
   │
   ▼
engine 集群（跑 RTD rule 的 Java 程序）
   │ 发 trigger 消息
   ▼
admin（读 ip/port）
   │ 更新各 sinker 的 trigger 配置
   ▼
sinker 重新加载配置

四、MES ↔ RTD 怎么通信

MES ──发布消息──▶ RabbitMQ ──▶ engine（定时拉取处理）
                                  │
                                  ▼
                             结果消息 ──▶ RabbitMQ ──▶ MES 取回

注意：这里和上面是两条不同的队列 —— 同步用 Kafka，RTD 调用用 RabbitMQ。别搞混。

五、我要能答得出的问题

  • [ ] 一批数据从 MES 到目标库，最长可能延迟多久？（各段相加）
  • [ ] 某张表不同步了，第一件事查哪？
  • [ ] Kafka 积压了，是生产快还是消费慢？
  • [ ] trigger 配置改了，谁去通知 sinker？
  • [ ] 主写库挂了，业务会怎样？

能答出这五个，这条链路就算真懂了。

  • [ ] 部署拓扑（几台、怎么分）

三步定位法

通用排查方法

任何故障都先走这三步，能解决 80% 的问题。

第一步：分清"是谁的问题"

系统里永远只有三种角色：

  1. 生产端（有人往里写吗？）
  2. 中间件（数据在管道里吗？）
  3. 消费端（有人取出来处理吗？）

先确认哪一段断了，别一上来就重启。

第二步：找"卡在哪个点"

按数据流顺序，从上游往下游推：

上游有没有数据产生？  没有 → 问题在上游
       │有
       ▼
中间件有没有积压？    积压 → 问题在消费端慢/挂
       │没积压
       ▼
下游有没有写入？      没写 → 问题在消费逻辑

每一步只需要一个判断，不要同时查三个。

第三步：确认改动前先备份

要动配置/重启之前：

  1. 先导出当前状态（ps、配置、库里的记录）
  2. 想清楚如果错了怎么退回去
  3. 再动手

没有回滚方案，就不要改生产。

什么时候用这个

场景 用哪步
数据不同步 第一 + 第二步
服务起不来 第一步（看日志）
慢了/积压 第二步
要改配置 第三步

一句话

先定位，再动手。 90% 的"越修越坏"，都是因为没定位就动手。

09

队列积压怎么查

最常见的故障

这是同步链路最常见的故障。别急着重启，先看数字。

先分清两种积压

现象 含义 方向
LAG 持续上涨 生产速度 > 消费速度 消费端性能问题
LAG 不涨也不降 消费端完全卡住 消费端挂了/死锁
LAG 归零但有延迟 队列正常，下游写入慢 查目标库

排查顺序（照做）

① 确认积压量

# Kafka
kafka-consumer-groups.sh --bootstrap-server <地址> --describe --group <组名>

看 LAG 那一列。

② 确认消费进程活着

ps -ef | grep <进程关键字> | grep -v grep

进程在 ≠ 在干活。 还要看：

top -p <PID>              # CPU 是不是一直很高（可能是死循环）
lsof -p <PID> | grep -c REG   # 打开的文件数是不是暴涨（可能句柄泄漏）

③ 看消费端日志

tail -n 200 <消费端日志> | grep -iE 'error|exception|timeout|retry'

④ 看下游

如果消费进程正常但就是慢：

  • 目标库连接池满了？（v$resource_limit）
  • 目标库有锁？（v$session 里 blocking_session）
  • 磁盘 IO 打满？（iostat -x）

三种典型结论

结论 A：消费进程挂了
→ 看日志找原因，修完重启。先确认生产端数据没丢。

结论 B：消费进程活着但处理慢
→ 看单条处理耗时。是不是某类数据特别慢？是不是 N+1 查库？

结论 C：一切正常但 LAG 就是高
→ 消费能力不够。加实例 或 提并发，别硬等。

⚠️ 不要做的事

  • ❌ 不要一上来就 --from-beginning 重读 —— 生产 IO 压力巨大
  • ❌ 不要先重置位移 —— 会丢数据或重复处理
  • ❌ 不要盲目扩容 —— 没找到瓶颈，扩容只是把问题推迟

半导体工艺流程

九大工艺 × 机台

从"流程"切入，不从"概念"切入。知道货怎么走，比背名词有用。

芯片的一生

硅石 → 提纯 → 单晶硅棒 → 切片研磨抛光 → 晶圆 Wafer
   → 前道 FEOL（造晶体管）
   → 中后道（连成电路）
   → 晶圆测试 CP
   → 切割 Dice
   → 封装 → 成品芯片

三层结构（别把"大类"当"步骤"）

层级 数量 说明
工艺大类 8~10 类 氧化、光刻、刻蚀、薄膜、注入、扩散、CMP、清洗
一个循环 约 15 道工序 光刻一层 + 配套
完整产品 800~1500 道 循环 40~80 次

九大工艺 + 机台

工艺 干什么 机台叫法 区域
氧化 长 SiO₂ 氧化炉 Furnace 扩散区
光刻 印图形 Scanner + Track 黄光区
刻蚀 刻出图形 Etcher 刻蚀区
薄膜 镀新材料 CVD / PVD / ALD 薄膜区
离子注入 掺杂质 Implanter 注入区
扩散/退火 激活杂质 炉管 / RTP 扩散区
CMP 磨平表面 CMP 机台 CMP 区
清洗 去污染 湿式清洗机 清洗区
量测 测尺寸/缺陷 CD-SEM、膜厚仪 量测区

一个循环长什么样（15 道）

清洗 → 淀积阻挡层 → 涂胶 → 软烘 → 曝光 → 曝后烘 → 显影 → 硬烘
→ 显影后检测 → 刻蚀 → 去胶 → 清洗 → CMP → 量测 → 缺陷检测

这只是"一层"。整颗芯片要循环 40~80 次。

派工为什么要管这些

工艺特点 对派工的影响
光刻是瓶颈、重入最多 优先保瓶颈不待料
